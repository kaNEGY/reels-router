# Сервис: первый этап

Это начало реализации: orchestrator принимает до десяти Instagram Reels, сохраняет задачу и команды в PostgreSQL и отправляет команды в Kafka через outbox. Media worker скачивает ролик, извлекает доступные метаданные и первую аудиодорожку и загружает артефакты в S3-совместимое хранилище. Ссылки очищаются от tracking-параметров. `Idempotency-Key` защищает от повторного создания одного и того же запроса; при другом содержимом ответ — 409.

После успешного media координатор ставит задачи отбора кадров и, если есть аудио, транскрибации в Kafka. Frames worker использует EmbeddingGemma и сохраняет кадры и оценки в S3. ASR, VLM, LLM и Geoapify вызываются из очередей orchestrator. LLM извлекает упоминания, геокодер возвращает кандидатов, а пользователь подтверждает или отклоняет каждый из них. Маршрутизация остаётся следующим этапом. Не направляйте прототип на общие рабочие топики: для теста нужны отдельные база/схема, топики и bucket.

Для ASR/текстовой/мультимодальной модели есть адаптер OpenAI-compatible API с независимыми настройками провайдера и модели. Если ASR, VLM, LLM или Geoapify не настроен, соответствующие команды ожидают обработчик в Kafka только в пределах срока хранения топика. Форматы, лимиты и поддержка изображений зависят от конкретного API. Для ASR по умолчанию установлен лимит `ASR_MAX_BYTES=25000000`; настройте его по ограничениям провайдера. Аудио большего размера пока не разбивается на части.

Распознанное название и его нормализованный вариант — гипотезы. Для каждого упоминания сохраняется точная цитата из исходных метаданных, транскрипта или описания кадра моделью. Цитата проверяется на наличие в источнике, но это не доказывает правильность нормализации или вывода VLM. Результаты геокодера — кандидаты, не подтверждённые места; его confidence не является вероятностью достоверности. Выбор отправляется через `POST /v1/jobs/{id}/selections` со списком `{"mention_id": "...", "candidate_id": "..."}`; `candidate_id: null` означает отклонение. Подтверждение доступно только для кандидата соответствующего упоминания.

Контекст поездки из запроса пока сохраняется в задаче, но не участвует в поиске и ранжировании кандидатов. Ручной ввод отсутствующего адреса и повторный запуск отдельного этапа также пока не реализованы.

## Настройка и запуск

Укажите параметры отдельной PostgreSQL и Kafka в локальном `.env` по образцу `.env.example`. Выберите `PG_SSLMODE` в соответствии с сервером; для Kafka с TLS используются `KAFKA_SECURITY_PROTOCOL=SSL` или `SASL_SSL`, при необходимости задайте CA-файл. Секреты не коммитятся. Подготовка базы выполняется **только** после проверки целевой базы и прав:

```sh
psql -h HOST -U USER -d DATABASE -v ON_ERROR_STOP=1 -f migrations/001_foundation.sql
psql -h HOST -U USER -d DATABASE -v ON_ERROR_STOP=1 -f migrations/002_media.sql
psql -h HOST -U USER -d DATABASE -v ON_ERROR_STOP=1 -f migrations/003_coordination.sql
psql -h HOST -U USER -d DATABASE -v ON_ERROR_STOP=1 -f migrations/004_outbox_backoff.sql
psql -h HOST -U USER -d DATABASE -v ON_ERROR_STOP=1 -f migrations/005_places.sql
```

Схема `reels_router` предназначена исключительно для приложения. Миграция ничего не удаляет, но создаёт таблицы и индекс; она не заменяет систему версионируемых миграций для дальнейшего развития схемы.

Для Compose задайте в `.env` существующую сеть `DOCKER_NETWORK`, существующий том весов `GEMMA_MODEL_VOLUME`, а также параметры отдельного bucket и топиков. Сам Compose PostgreSQL, Kafka, MinIO и сеть не создаёт. Bucket и его lifecycle настраиваются отдельно администратором: приложение не включает автоудаление. На тестовом bucket проверено правило удаления объектов через 7 дней. Затем можно выполнить `docker compose up --build`; API доступен только на loopback хоста. Для приватных Reels файл cookies нужно монтировать отдельно и передать путь через `INSTAGRAM_COOKIES_FILE`, не помещая cookies в образ.

```sh
python -m pip install -r requirements.txt
PYTHONPATH=src uvicorn reels_router.main:app --host 127.0.0.1 --port 8000
```

Пример запроса к локальному сервису:

```sh
curl -X POST http://127.0.0.1:8000/v1/jobs \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: example-1' \
  -d '{"urls":["https://www.instagram.com/reel/De4IKljoBfq/"]}'
```

`GET /v1/jobs/{job_id}` возвращает состояние; `/docs` содержит контракт API. Повтор с тем же ключом и содержимым возвращает 200, новая задача — 202. `completed` означает, что кандидаты рассмотрены, а не что построен маршрут. Сервис не имеет авторизации: помимо loopback хоста он доступен участникам общей Docker-сети, поэтому до расширения доступа нужна защита. `/health/live` проверяет процесс; `/health/ready` проверяет БД и фоновые корутины, но не гарантирует текущую доступность Kafka и других зависимостей.

Для отладки предусмотрен `POST /internal/stages/{kind}` с `job_id`, `video_id` и `artifact_ids`: этап попадает в ту же Kafka через outbox. Допустимые `kind`: `media`, `frames`, `asr`, `vlm`, `llm`, `geo`; идентификаторы артефактов доступны в ответе о задаче. Эндпоинт требует `X-Internal-Token`, совпадающий с `INTERNAL_API_TOKEN`, и без токена отключён. Входы проверяются на принадлежность ролику, повторно поставить уже существующую команду нельзя; полноценного API повторного запуска пока нет.

Отправка в Kafka выполняется после сохранения данных в транзакции. Сбой после отправки, но до отметки в БД может привести к повтору; завершённые этапы дедуплицируются по `stage_id`. Ошибка публикации откладывает повтор на пять секунд и не должна блокировать другие топики. Ошибки этапа повторяются до трёх раз, затем фиксируются в БД и outbox. При сбое между загрузкой в S3 и фиксацией в БД может остаться объект без ссылки; удаление зависит от lifecycle bucket. Полноценные leases, восстановление зависших этапов, DLQ, общий rate limit и возобновление частично оплаченных запросов ещё не реализованы. Повтор VLM может вызвать платные запросы повторно. Порядок обработки между топиками не гарантируется.

## Проверка

```sh
python -m pip install -r requirements-test.txt
PYTHONPATH=src python -m pytest tests
docker build -f docker/orchestrator.Dockerfile -t reels-router-orchestrator:local .
docker build -f docker/media.Dockerfile -t reels-router-media:local .
docker build -f docker/frames.Dockerfile -t reels-router-frames:local .
```

Тесты API в CI используют подставной репозиторий. В интеграционных проверках использованы настоящие PostgreSQL, Redpanda и MinIO с отдельными тестовыми базами, топиками и bucket. Проверены идемпотентность, повтор неудачной публикации, FFmpeg, загрузка артефактов, Gemma CPU и выбор кандидата. В сквозном прогоне скачивание и внешние API были подменены, а инфраструктура, FFmpeg и Gemma работали настоящие. Отдельно проверены реальный запрос Geoapify и преобразование аудио скачанного Reels в FLAC. Доступность Instagram зависит от сетевого окружения; автоматического обходного пути в сервисе нет. Скрипты используют тестовые ресурсы и не предназначены для рабочей базы или топиков. Внешние API и тяжёлые модели в CI не вызываются.
