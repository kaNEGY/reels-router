# Правила совместной работы

## Ветки и ревью

Все изменения выполняются в отдельных feature-ветках от актуального `main` и попадают в `main` только через pull request (PR). Это относится к коду, данным, ноутбукам, документации и CI.

1. Обновите локальный `main` и создайте ветку с понятным названием: `feat/asr`, `fix/geocoding`, `data/pilot`, `docs/checkpoint-2` или `ci/markdown`.
2. Сделайте связные коммиты и выполните проверки, соответствующие изменениям.
3. Отправьте ветку и откройте PR в `main`. Укажите, что изменилось, как проверено и какие ограничения остались. Запросите ревью другого участника команды.
4. Перед merge должны пройти все включённые проверки CI и быть получено хотя бы одно одобрение (`Approve`) от другого участника команды. Автор PR не одобряет собственную работу.
5. Исправьте замечания. Если после одобрения внесены содержательные изменения, запросите повторное ревью. Только после этого выполняется merge.

Прямые push в `main` не используются. Не делайте force push в общие ветки. Ветка одного PR должна решать одну понятную задачу; крупную работу делите на небольшие проверяемые части.

Это обязательное командное правило. Техническая блокировка прямых push и merge без одобрения настраивается отдельно владельцем репозитория через GitHub Rulesets / Branch protection. Наличие этого документа само по себе не включает защиту ветки.

## Коммиты

Формат: `type(scope): описание`. Scope необязателен; описание пишем по-русски, после двоеточия используем существительное или именную конструкцию: «добавление», «исправление», «обновление».

| Тип | Когда применять |
| --- | --- |
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Документация и пояснения |
| `data` | Разметка, метаданные и версии разрешённых к публикации данных |
| `test` | Проверки и тесты |
| `ci` | Автоматические проверки |
| `refactor` | Изменение структуры кода с сохранением поведения |
| `chore` | Зависимости и обслуживание проекта |

Примеры:

```text
docs: уточнение плана второго чекпоинта
data: добавление разметки пилотной выборки
feat(asr): добавление транскрибации видео
fix(geocoding): исправление выбора одноимённых мест
test(routing): добавление проверки длительности маршрута
ci: добавление проверки Markdown
```

Один коммит — одно связное изменение. Перед коммитом просматривайте `git diff` и `git diff --staged`; добавляйте конкретные файлы. Заголовок PR и сообщение squash-коммита оформляйте по тем же правилам. Автоматическая проверка формата коммитов пока не включена.

## Данные и ноутбуки

- Не публикуйте секреты, cookies, `.env`, локальные окружения, веса моделей и исходные видео. Для данных сначала проверьте условия хранения и публикации.
- Небольшие аннотации и метаданные можно хранить в Git после проверки состава и прав на публикацию. Указывайте версию выборки, происхождение данных и правила разметки.
- Перед сдачей запускайте ноутбук с начала до конца в описанном окружении. Сохраняйте нужные графики, таблицы и выводы; удаляйте отладочный вывод, ошибки и чувствительные данные.
- В описании эксперимента фиксируйте данные, версии моделей, настройки, метрики и ограничения. Не подбирайте параметры по final test set.
- Личные планы, журналы сессий и локальные инструкции остаются вне репозитория.

## CI и локальная проверка

GitHub Actions запускает проверку Markdown при push в ветки и при открытии или обновлении PR. Используется стандартный GitHub-hosted runner `ubuntu-latest`: отдельная VM команды не требуется. Workflow имеет только доступ на чтение репозитория.

Для той же проверки локально нужен Node.js 22 или новее:

```sh
npx --yes markdownlint-cli2@0.23.3
```

Правила и список файлов заданы в `.markdownlint-cli2.jsonc`. Ограничение длины строки отключено. Эта проверка оценивает оформление Markdown; корректность выводов, ссылок и результатов проверяет ревьюер.

По мере появления кода добавим Ruff и быстрые тесты. Тяжёлые модели, GPU и платные API в обычном CI не запускаются. Проверка наличия материалов чекпоинта и выполнение EDA будут добавлены, когда появятся сами материалы и воспроизводимое окружение.
