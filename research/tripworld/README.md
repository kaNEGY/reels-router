# TripWorld: EDA для Reels Router

**Вывод**: TripWorld подходит для экспериментов с рекомендацией POI и порядком посещения. Для оценки извлечения конкретного места из Reels его недостаточно: в исследованных таблицах нет видео, транскриптов и разметки упоминаний. Проверили пять полных таблиц, а не выборку первых строк. Дата проверки: 28 октября 2026.

**Источник и версия**: исходная [карточка neolifer](https://huggingface.co/datasets/neolifer/TripWorld) указывает на [CRUISEResearchGroup/TripWorld](https://huggingface.co/datasets/CRUISEResearchGroup/TripWorld). Использовали последнюю версию этой публикации на момент проверки: `421bc1dc63068bb398055b1ce987265fe22415db`, манифест от 1 июня 2026. У зеркала neolifer более поздняя дата изменения, но другой состав файлов и размеры. Данные двух публикаций не смешивали. Все числа ниже рассчитаны скриптом [eda.py](eda.py); полные схемы, nulls по каждому столбцу, распределения и SHA-256 сохранены в [metrics.json](results/metrics.json).

**Что уже сделано командой**: прочитали README, CONTRIBUTING и три notebook в `main` на коммите `feace236`. PR [#5](https://github.com/kaNEGY/reels-router/pull/5) содержит Google Landmarks Places, PR [#6](https://github.com/kaNEGY/reels-router/pull/6) - Overture, OSM, Wikidata и разбор дополнительных источников. TripWorld в этих notebook отсутствует. ATD-MCL исключили: для восстановления текстов нужна [заявка на исходный ATD](https://sites.google.com/view/geography-and-language/resources), доступ ограничен академическим исследованием. По согласованному скоупу исследовали только TripWorld.

**Объем и схема**: скачали 420 945 705 байт Parquet, проверили размеры, контрольные суммы и число строк по закрепленному MANIFEST. Отзывы `reviews_all.parquet` на 23,4 ГБ не скачивали; их тексты, язык, дубликаты и качество не оценивали.

**Единица наблюдения**: 518 567 строк описывают пары «пользователь - домашний регион - регион назначения» для 148 402 пользователей. Это не число поездок или дневных маршрутов. Поля `c_h` и `c_o` содержат последовательности check-ins дома и в регионе назначения; один список может включать несколько `trail_id`. Это проверили по данным и коду `_scripts/04_build_travel_behaviors.py`. Определение домашнего региона алгоритмическое, а не подтвержденное пользователем.

**География**: в справочнике регионов 51 непустое название страны, а не заявленные в README «90+». Через связь `pois.locality = regions.region_id` получаем 287 281 POI в Японии, 100 154 в Турции и 58 750 в Малайзии: вместе 64,93% каталога. В Токио 69 935 POI, Стамбуле 20 943, Осаке 20 544. Это распределение записей каталога, не туристов и не роликов.

**Российское покрытие**: через справочник регионов к Russia привязываются 1 309 POI: Moscow - 630, Centralniy - 341, Q39165706 - 201, Q39266317 - 137. Эти подписи нельзя автоматически считать полными административными границами. По координатному прямоугольнику Петербурга (59,7-60,15 N; 29,5-30,7 E) получаем 542 записи. Это отдельный пространственный фильтр, не число достопримечательностей города и не административная выборка.

**Категории**: в `venue_schema` 160 различных непустых значений. Наиболее частые: Restaurant - 143 974, CivicStructure - 51 935, FoodEstablishment - 51 536, CafeOrCoffeeShop - 43 911, BarOrPub - 35 121. Каталог включает жилье, транспорт и повседневные заведения. Эти категории нельзя использовать как готовую разметку туристической привлекательности.

**Пропуски и связи**: у восьми POI отсутствуют координаты FSQ и имя FSQ; у трех нет ни имени FSQ, ни имени Google. Еще одна запись имеет координаты (0, 0) и имя `_`. Координат вне допустимых диапазонов или бесконечных значений не нашли; точность положения объектов на местности не проверяли. У 120 375 POI нет `google_name`, у 118 031 нет `fsq_address`, еще у 2 697 адрес пустой. У 13 755 POI `locality` не находится в справочнике регионов; после join страна неизвестна для 18 265 POI. У 218 регионов вместо названия города записан QID, у девяти отсутствует страна.

**Проверка названий**: `benchmark_name` содержит 605 581 строку формата 24-символьного hex-ID (88,13% каталога); использовать этот столбец как текстовое имя нельзя. Для поиска подходят `fsq_name` и доступные `google_name`, с отдельной проверкой неоднозначности. После lower/trim повторяются 28 127 имен, охватывающих 131 834 строки. Это не автоматически дубли: в просмотренных примерах Starbucks имеет разные координаты. У девяти групп совпадают нормализованное имя и точные координаты, с 12 лишними строками; это кандидаты на ручное сопоставление.

**Дубликаты и ключи**: во всех пяти таблицах нет полностью одинаковых строк и повторов выбранных ключей: `fsq_place_id`, `region_id`, либо `(user_id, r_h, r_o)`. Ключевые поля заполнены. Связь POI с metadata полная в обе стороны, все ID из attributes найдены в POI. Все check-ins назначения ссылаются на существующий POI. Эти проверки не исключают семантические дубли объектов с разными ID.

**Свежесть**: check-ins датированы 3 октября 2017 - 20 октября 2018, хотя публикация выпущена в 2026 году. У 33 877 POI заполнена дата закрытия FSQ (4,93%). `fsq_date_refreshed` варьируется от 2013-05-06 до 2027-06-21; одна запись имеет дату позже дня проверки (Hop Inn, Thailand). Причина аномалии не установлена. Обогащенные атрибуты получены 2 мая 2026; недельные часы отсутствуют у 8 229 из 28 776 строк, `price_min` и `price_max` пусты во всех строках. Текущие часы, цены и доступность из этого снапшота не следуют.

**Расхождение с карточкой**: фактически флаг `has_google_metadata` установлен у 566 798 POI (82,48%), и для них заполнено имя Google. В README указаны 309 941 и 45%. Для данной версии используем пересчитанное значение; качество сопоставления FSQ с Google целиком не подтверждено. В attributes нет записей с `match_dist_m > 1 000` или `match_name_sim < 0,5`, но это только диагностика сохраненных оценок, не ручная проверка совпадений.

**Последовательности**: в `c_o` 2 764 448 check-ins, 377 176 POI и 1 279 921 уникальный `trail_id`. Пропусков времени, POI, категории или ID сессии, повторов ключа `(user_id, trail_id, venue_id, ts)` и одинакового времени внутри `(user_id, trail_id)` не нашли. Длины `c_h`/`c_o` совпадают с соответствующими счетчиками во всех строках. Медиана длины `c_o` - три check-ins, максимум - 744.

**Ограничения сессий**: при группировке по `(user_id, trail_id, r_o)` получаем 1 613 361 сегмент; 900 929 состоят из одного check-in (55,84%), 916 610 относятся к одному уникальному POI. У 258 509 пар `(user_id, trail_id)` check-ins назначения встречаются в нескольких регионах. У 17 452 сегментов интервал между первым и последним check-in превышает сутки; максимум 7 064,7 часа. Поэтому `trail_id` нельзя без дополнительной сегментации трактовать как однодневный туристический маршрут. Домашняя последовательность используется повторно в строках одного пользователя: 96 763 пары `(user_id, r_h)` охватывают 466 928 строк. Случайное разбиение строк создает риск утечки; baseline ниже разделяет пользователей.

**Просмотр примеров**: сохранили восемь POI с максимальным числом check-ins в разных странах и пять строк с повторяющимся именем в `metrics.json`. В примерах есть Akihabara Station в Токио, Grand Avenue в Kuwait City и аэропорты. В строке Grand Avenue имя Google содержит уточнение «Entrances 20»: совпадение имен разных источников не гарантирует одинаковую гранулярность POI. Такая выборка помогает увидеть структуру, но не дает оценки доли ошибочных сопоставлений.

**Измеренный baseline**: ранжируем POI внутри известного региона назначения по числу уникальных пользователей в train, затем по числу check-ins; при равенстве используем `venue_id` по возрастанию. Train: пользователи с `user_id % 5 != 0`; test: остальные. Цель - последний POI каждого тестового сегмента `(user_id, trail_id, r_o)` с минимум двумя check-ins. Параметры по test не подбирали. Получили 142 026 целей от 26 928 пользователей: Hit@1 = 10 424 / 142 026 = 7,34%, Hit@5 = 27 661 / 142 026 = 19,48%. У 16 810 целей POI не встречается в train данного региона. Это диагностическая задача рекомендации последнего POI с известным регионом; модель не использует историю тестового сегмента. Метрика не оценивает качество извлечения POI из Reels или удобство маршрута.

**Применимость**: можно сравнить этот popularity baseline с персонализированным ранжированием и предсказанием следующего POI. Для поиска по речи/OCR каталог дает имена и координаты, но оценка потребует собственной разметки «фрагмент текста - ID POI» и проверки покрытия выбранного города. Для упорядочивания подтвержденных точек можно начать с ближайшего соседа; дорожное время, транспорт, входы, длительность посещений и актуальные часы нужно получать отдельно. Последовательность check-ins не является оптимальным или рекомендованным маршрутом.

**Запуск**: Python 3.9+, `curl`, DuckDB 1.4.3; команды из корня репозитория. Первая команда загрузки обращается к закрепленной версии последовательно и пишет каждый запрос в `requests.log`. Повтор с недоступным адресом проверяет локальный кеш без загрузки. Сам EDA сети не использует. Прогресс пишется в `eda.log`; результаты содержат данные пяти полных таблиц, без случайного семплирования. Проверили полный запуск и повтор из кеша: JSON-результаты совпали.
