# Мультимодальное определение геолокации по коротким туристическим видео

[Правила работы, коммитов и ревью](CONTRIBUTING.md) · [Чекпоинт 2](#чекпоинт-2--eda-и-практическая-ценность) · [CI](https://github.com/kaNEGY/reels-router/actions)

Все изменения — через отдельные feature-ветки и PR в `main`, с успешным CI и одобрением другого участника команды.

## Описание проекта

Короткие видео в формате Instagram Reels, TikTok и YouTube Shorts все чаще становятся источником идей для путешествий. Пользователи сохраняют ролики с интересными местами, но затем вынуждены вручную определять показанные локации, искать их на карте и составлять маршрут.

Цель проекта — разработать end-to-end систему, которая автоматически определяет локации, показанные или упомянутые в коротких туристических видео, а затем использует найденные точки для построения маршрута.

Проект объединяет методы компьютерного зрения, распознавания речи, OCR, обработки естественного языка и мультимодального моделирования. Итоговым результатом должен стать работающий прототип с измеримым качеством определения локаций и пользовательским интерфейсом — в первую очередь Telegram-ботом или Telegram Mini App.

## Постановка задачи

На вход система получает одно или несколько коротких туристических видео. Для каждого видео необходимо:

1. извлечь потенциально полезные сигналы;
2. определить наиболее вероятную реальную локацию или точку интереса;
3. оценить уверенность модели в предсказании;
4. объединить найденные локации из нескольких видео;
5. построить практический маршрут между выбранными точками;
6. представить результат пользователю в удобном формате.

Планируем принимать ссылки на доступные публикации и локальные видеофайлы. Доступность загрузки по ссылке проверяется на пилоте; у локального файла подпись публикации может отсутствовать. Если ссылка недоступна, система предлагает загрузить файл или пропустить ролик. Подпись и теги используем только при их фактической доступности.

Основная цель — не грубое определение страны или региона, а распознавание конкретного места: достопримечательности, объекта городской инфраструктуры, заведения или другой точки интереса.

Для первой версии проекта задача будет намеренно ограничена одним географическим регионом. Это позволит собрать качественный датасет, получить интерпретируемые метрики и корректно сравнить различные подходы до расширения системы на более широкую географию.

## Цели проекта

Проект включает две взаимосвязанные части: исследовательскую и продуктовую.

### Исследовательская цель

Определить, какие источники информации и какие модельные подходы наиболее полезны для определения локации по короткому туристическому видео.

Планируется сравнить:

- извлечение текста с помощью OCR;
- распознавание речи и анализ транскрипта;
- визуальное определение локации и landmark recognition;
- метаданные и подписи к видео, если они доступны;
- мультимодальные комбинации текстовых, аудио- и визуальных сигналов.

Основной исследовательский вопрос:

> Насколько объединение нескольких модальностей улучшает качество определения локации по сравнению с использованием каждой модальности отдельно?

Дополнительные вопросы:

- какая модальность дает наиболее сильный baseline;
- в каких случаях OCR или ASR достаточно без анализа изображения;
- дают ли специализированные geo-модели преимущество над универсальными vision-language моделями;
- какой способ объединения модальностей дает лучший баланс качества, стоимости и задержки;
- насколько надежно можно калибровать confidence score и использовать его в продукте.

### Продуктовая цель

Создать работающий прототип, который принимает пользовательские видео, определяет конкретные локации с приемлемой точностью и строит маршрут по найденным точкам.

## Границы первой версии

### Входит в MVP

- короткие туристические видео;
- один основной географический регион;
- одна доминирующая локация на видео;
- достопримечательности и узнаваемые точки интереса;
- извлечение доступных подписей, OCR и ASR; визуальный анализ добавляется по результатам экспериментов;
- мультимодальное ранжирование кандидатов;
- оценка уверенности модели;
- получение координат найденных мест;
- подтверждение или исправление неоднозначных мест пользователем;
- построение маршрута по нескольким видео;
- Telegram-интерфейс;
- воспроизводимая оценка качества на вручную проверенном тестовом наборе.

### Не входит в первую версию

- геолокация без географических ограничений по всему миру;
- определение точных координат камеры для произвольной уличной съемки;
- надежное распознавание нескольких независимых локаций внутри одного ролика;
- обработка видео в реальном времени;
- автоматическое бронирование гостиниц, билетов или активностей;
- полноценное production-развертывание.

Видео с несколькими независимыми локациями на первом этапе будут либо исключены из основного benchmark, либо выделены в отдельный экспериментальный сценарий. При наличии времени можно добавить поддержку нескольких предсказаний для одного видео или возможность указать, какую часть ролика необходимо анализировать.

## Работа с данными

Отдельный этап проекта посвящен данным, поскольку заранее неизвестно, насколько существующие открытые датасеты соответствуют задаче геолокации коротких туристических видео из социальных сетей.

План работы:

1. изучить открытые датасеты по landmark recognition, visual geolocation и туристическому контенту;
2. проверить, насколько их распределение данных соответствует целевой продуктовой задаче;
3. выбрать один регион для MVP;
4. собрать собственный набор реальных коротких видео с известными локациями;
5. определить единый протокол разметки;
6. разделить данные на development- и final evaluation-части;
7. контролировать дисбаланс классов и наличие дубликатов.

До сбора и публикации проверяем условия использования источников. Разделяем данные по авторам или поездкам с учётом репостов и близких дубликатов. Выбор моделей, весов fusion и порогов confidence выполняется на dev; final test фиксируется отдельно и не используется для настройки. Данные, вручную разобранные при EDA для выбора подходов, считаем development-данными; финальную отложенную выборку формируем отдельно.

Даже если открытый датасет будет использован для обучения или предварительных экспериментов, для финального тестирования необходим вручную проверенный набор реальных Reels, TikTok или Shorts, поскольку именно он лучше отражает целевой пользовательский сценарий.

### Предлагаемая схема разметки

Для каждого видео предполагается хранить следующие поля, если они доступны:

- идентификатор видео;
- источник;
- основное название локации;
- город;
- регион;
- страна;
- широта и долгота;
- категория точки интереса;
- альтернативные допустимые названия;
- наличие текстовых подсказок в кадре;
- наличие географических подсказок в речи;
- визуальная узнаваемость локации;
- количество различных мест в видео;
- уверенность в корректности разметки.

Целевой POI — конкретное место, показанное или явно рекомендованное как объект посещения. Простое упоминание другого места не делает его целевым. Для каждого кандидата фиксируем роль (`shown`, `recommended`, `mentioned`), идентификатор в геобазе, источник доказательства и таймкод либо фрагмент подписи. Если единственный целевой POI выбрать нельзя, пример помечаем `ambiguous` или `unknown` и рассматриваем отдельно; правило выбора и спорные случаи фиксируем в инструкции разметчикам. Часть примеров независимо размечают два участника и разбирают расхождения.

## Предлагаемая архитектура

```text
Ссылка / видеофайл
  ├─ Подпись и теги (если доступны) ────────────────┐
  ├─ Аудио → ASR → транскрипт с таймкодами ─────────┤
  └─ Кадры ┬─ OCR → экранный текст с таймкодами ────┤
           └─ Visual model → визуальные кандидаты ┤
                                                  ↓
           Извлечение названий и поиск кандидатов в геобазе
                                                  ↓
           Проверка контекста, объединение сигналов, ранжирование
                                                  ↓
           Конкретный POI с координатами / needs_review / unknown
                                                  ↓
           Подтверждение, исправление или пропуск пользователем
                                                  ↓
           Дедупликация → время между точками → дневной план → карта
```

OCR работает непосредственно с кадрами, параллельно визуальной модели. Геокодирование названия может возвращать несколько кандидатов: их проверяем по региону, типу объекта и контексту до выдачи окончательного POI и уверенности. Если retrieval сразу возвращает ID из каталога, координаты берём из записи каталога.

Сначала собираем простой сквозной pipeline, затем сравниваем вклад дополнительных сигналов. Специализированные geo-модели исследуем, но их внедрение не обязательно: отсутствие полезного прироста тоже является результатом эксперимента.

## Baseline-подходы

Перед использованием сложных мультимодальных моделей необходимо построить несколько простых и интерпретируемых baseline.

### Baseline по подписи публикации

1. получить доступные описание и теги;
2. извлечь названия мест;
3. найти кандидатов в геобазе и проверить контекст;
4. вернуть POI или отказ от однозначного ответа.

Отдельно считаем долю роликов, для которых подпись вообще доступна.

### OCR baseline

1. извлечь набор кадров из видео;
2. применить OCR;
3. найти географические сущности в распознанном тексте;
4. сопоставить их с базой известных локаций;
5. сформировать и ранжировать кандидатов.

### Аудио baseline

1. извлечь аудиодорожку;
2. получить транскрипт с помощью ASR;
3. найти географические сущности в тексте;
4. сопоставить найденные сущности с кандидатами на локацию.

### Визуальный baseline

Возможные подходы:

- image-text retrieval по эмбеддингам;
- landmark classification;
- поиск ближайших соседей среди известных локаций;
- использование vision-language моделей;
- специализированные модели визуальной геолокации.

### Мультимодальный baseline

На первом этапе оценки разных модальностей можно объединять через простую взвешенную схему ранжирования кандидатов. Более сложные методы fusion имеет смысл тестировать после появления устойчивых single-modality baseline.

## Оценка качества

Обычной бинарной метрики «верно / неверно» для задачи геолокации недостаточно. Ошибка внутри правильного города существенно отличается от ошибки на уровне страны, однако для продукта простого определения страны также недостаточно.

Поэтому предполагается многоуровневая система оценки.

### Основные метрики

- accuracy точного определения точки интереса;
- top-k accuracy;
- accuracy на уровне города;
- accuracy на уровне региона;
- accuracy на уровне страны;
- среднее географическое расстояние между предсказанной и истинной точкой;
- медианное географическое расстояние;
- метрики калибровки confidence score;
- coverage — доля примеров с автоматическим ответом, и accuracy среди этих ответов;
- частота уверенных ошибок и качество обработки `unknown` на отдельно размеченных примерах.

Основные метрики — совпадение канонического POI и top-k accuracy. В ограниченном регионе показатели города/страны сравниваем с постоянным ответом: если весь тест из одного города, такие показатели не доказывают распознавание. Географические ошибки считаем на примерах с известными координатами и выданным ответом, отдельно сообщая coverage. Пропуск разрешимого примера не считается успешным определением POI.

### Иерархический score

Для частично правильных ответов можно использовать дополнительный взвешенный score.

Рабочий вариант:

```text
Точная точка интереса   1.00
Правильный город        0.50
Правильный регион       0.25
Правильная страна       0.10
Неверная страна         0.00
```

Конкретные веса являются рабочим допущением и должны быть пересмотрены после анализа данных и с учетом продуктовой полезности разных уровней точности.

### Сравнение модальностей

Проводим ablation study, начиная с доступных текстовых сигналов:

```text
Caption; OCR; ASR; Visual — отдельные baseline
Caption + OCR
Caption + ASR
OCR + ASR
Caption + OCR + ASR
Caption + OCR + ASR + Visual
```

Сравниваем варианты на одинаковых примерах, фиксируем отсутствующие модальности и дополнительно показываем срезы по доступности подписи, речи и экранного текста. Для visual отдельно исследуем влияние читаемых надписей в кадрах: VLM может использовать их даже без отдельного OCR. Измеряем прирост качества, стоимость и задержку, а не только итоговую accuracy.

## Принципы выбора моделей

Модель не должна выбираться только потому, что она популярна или показывает сильные результаты на сторонних benchmark. Выбор каждого ключевого компонента должен быть обоснован литературным обзором и экспериментами на данных проекта.

Основные критерии:

- качество на нашем benchmark;
- inference latency;
- вычислительная стоимость;
- размер модели;
- сложность развертывания;
- зависимость от внешних API;
- воспроизводимость;
- пригодность для выбранного региона;
- лицензионные ограничения.

Предпочтение должно отдаваться наиболее простому решению, которое обеспечивает достаточное качество для целевого продуктового сценария.

## Построение маршрута

В маршрут включаем подтверждённые POI. Перед расчётом запрашиваем число дней, доступное время в день, способ передвижения и старт/финиш. Для каждой точки задаём хотя бы приблизительную длительность посещения и возможность её пропуска; предположения видны пользователю.

Первая версия поддерживает дедупликацию, упорядочивание точек по времени в пути, распределение по дням с учётом времени посещений и отображение на карте. Если всё не помещается, показываем пропущенные точки и причину. Недостижимые переходы не считаем нулевыми по времени.

Первый baseline — простая эвристика с дневным бюджетом. Кандидаты на дальнейшую реализацию: OSRM для матрицы перемещений по дорожной сети с подходящим транспортным профилем и OR-Tools для выбора порядка и временных ограничений. Расписания общественного транспорта требуют отдельного источника. Часы работы добавляем при наличии данных; проверяем соблюдение ограничений, покрытие желаемых POI и суммарное время перемещений.

Кафе, отели и дополнительные активности рядом с маршрутом можно добавить позднее как отдельные рекомендации. Актуальные цены и наличие мест требуют подходящего источника; они не следуют из распознавания ролика.

## Технический стек

Финальный набор технологий может измениться по результатам исследования. На старте рассматривается следующий стек:

- Python;
- PyTorch;
- Hugging Face ecosystem;
- OpenCV / FFmpeg для обработки видео;
- OCR-модель или OCR API;
- Whisper или другая ASR-модель;
- векторный поиск для image/text retrieval;
- API геокодирования и маршрутизации;
- FastAPI для inference API;
- Telegram Bot API или Telegram Mini Apps;
- Docker для воспроизводимого развертывания;
- система трекинга экспериментов.

Если вычислительные требования окажутся выше доступных команде ресурсов, после оценки необходимой инфраструктуры планируется сформировать запрос на дополнительные ресурсы со стороны университета.

## Основные риски

### Отсутствие подходящего открытого датасета

**Риск:** существующие датасеты могут плохо соответствовать коротким видео из социальных сетей.

**Митигирующее действие:** использовать открытые данные для предварительных экспериментов или обучения, но отдельно собрать собственный вручную проверенный benchmark.

### Недостаток визуальной информации

**Риск:** часть роликов может содержать типовые городские или природные сцены без уникальных ориентиров.

**Митигирующее действие:** использовать комбинацию изображения, OCR, ASR и доступных метаданных, а также разрешить системе возвращать низкую уверенность или статус `unknown` вместо принудительного предсказания.

### Несколько локаций в одном видео

**Риск:** один ролик может показывать несколько городов или достопримечательностей.

**Митигирующее действие:** на первом этапе исключить такие случаи из основного benchmark или рассматривать их как отдельное расширение задачи.

### Стоимость API и вычислений

**Риск:** сильные мультимодальные модели могут быть дорогими для регулярного inference.

**Митигирующее действие:** отдельно измерять стоимость, latency и качество open-source и API-решений; при необходимости обосновать запрос дополнительных вычислительных ресурсов.

### Переобучение на выбранный регион

**Риск:** решение, хорошо работающее в ограниченной географии, может плохо переноситься на другие регионы.

**Митигирующее действие:** рассматривать выбранный регион как контролируемую исследовательскую среду и после стабилизации системы отдельно проверить переносимость на дополнительную географию.
